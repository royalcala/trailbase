# Schema Architecture

TrailBase provides a clear separation between **system schemas** (managed by TrailBase)
and **application schemas** (your business logic).

## Directory Structure

```
traildepot/
├── schema/
│   ├── system/            # ⚠️ Auto-generated (regenerate with `trail schema export`)
│   │   ├── main.sql      # Core: _user, _org, _org_membership, _session, ...
│   │   └── org.sql       # Org-scoped system tables (if multi-org)
│   │
│   └── app/              # ✅ Your application (edit these)
│       ├── main.sql      # Your tables: contracts, properties, etc
│       └── org.sql       # Org-scoped: org_contracts, org_properties, etc
│
├── migrations/
│   ├── main/             # Migration history for main.db
│   │   └── U*.sql
│   │
│   └── orgs/             # Per-org migrations (if multi-org)
│       └── org_<slug>/
│           └── U*.sql
│
└── data/
    ├── main.db           # Primary database
    ├── org_*.db          # Per-organization databases (if multi-org)
    └── backups/
```

## Why This Separation?

**System Schemas** (`system/`):
- Generated by TrailBase to provide core functionality
- Contains internal tables (`_user`, `_org`, etc) and system-level infrastructure
- Automatically regenerated when TrailBase updates
- **Never edit manually** — changes will be overwritten

**Application Schemas** (`app/`):
- Your business logic and domain models
- Edited by development teams
- Source of truth for your data models
- migrations are generated only from changes here

## Understanding Schema Composition

When TrailBase initializes a database, it applies both the system and application schemas:

```
final_schema = system_schema + app_schema
```

For databases:
- **main.db**: `system/main.sql` + `app/main.sql`
- **org_*.db** (multi-org): `system/org.sql` + `app/org.sql`

## Workflow: Updating Your Application Schema

### 1. Modify Application Schema

Edit `traildepot/schema/app/main.sql` or `traildepot/schema/app/org.sql`:

```bash
# Add a new table or modify existing ones
vim traildepot/schema/app/main.sql
```

### 2. Plan Changes

Preview what migrations will be generated:

```bash
trail declarative plan --db main --schema traildepot/schema/app/main.sql
```

### 3. Apply Changes

Generate and apply migrations:

```bash
trail declarative apply --db main --schema traildepot/schema/app/main.sql
```

This creates a new migration file in `migrations/main/` following the pattern:
`U<timestamp>__schema_sync.sql`

### 4. Commit Changes

```bash
git add traildepot/schema/app/ traildepot/migrations/main/
git commit -m "feat(schema): add contracts table"
```

## Workflow: Syncing TrailBase Updates

When you update TrailBase to a new version, you should sync the system schemas
to ensure you have the latest system tables and features.

### 1. Export Current System Schema

```bash
trail schema export > traildepot/schema/system/main.sql
```

<Aside type="note">
  This command exports the schema from the currently running TrailBase instance.
  If multi-org is enabled, you may also want to export org schema:
  `trail schema export --org > traildepot/schema/system/org.sql`
</Aside>

### 2. Review Changes

```bash
git diff traildepot/schema/system/main.sql
```

This shows you exactly what changed in TrailBase's core tables and features.

### 3. Test Compatibility

Ensure your application schema is compatible with the new system schema:

```bash
trail declarative plan --db main --schema traildepot/schema/app/main.sql --check
```

### 4. Commit the Sync

```bash
git add traildepot/schema/system/main.sql
git commit -m "chore(trailbase): sync system schemas v1.2.3 → v1.3.0"
```

## Multi-Org Considerations

In multi-org mode, TrailBase maintains separate databases per organization:

- **main.db**: Global identity and org management (from `system/main.sql` + `app/main.sql`)
- **org_*.db**: Organization-specific data (from `system/org.sql` + `app/org.sql`)

### Org-Scoped Migrations

When you modify `traildepot/schema/app/org.sql`, migrations are generated for each org:

```
traildepot/migrations/orgs/org_<slug>/U<timestamp>__*.sql
```

TrailBase applies these migrations:
- **Lazy**: When an org is first accessed (opened)
- **Startup sweep**: Before startup completes, if configured

### System vs Application in Org Databases

Both system and application schemas are applied to org databases:

```
org_<slug>.db schema = system/org.sql + app/org.sql
```

Only `app/org.sql` changes generate migrations. The `system/org.sql` provides
the baseline that TrailBase manages.

## Best Practices

<Aside type="caution">
  **Never manually edit `system/` files.** They are regenerated from TrailBase
  internals and manual changes will be lost on the next sync.
</Aside>

1. **Always edit `app/` for business logic**
   - Use `traildepot/schema/app/main.sql` for main database tables
   - Use `traildepot/schema/app/org.sql` for org-scoped tables

2. **Commit system schema changes**
   - Track `system/` in version control for audit trail
   - Allows teams to see TrailBase evolution over time

3. **Use declarative workflow**
   - Prefer `trail declarative plan/apply` over manual migrations for consistency
   - Ensures migrations are generated correctly from schema diffs

4. **Monitor breaking changes**
   - When upgrading TrailBase, review `git diff system/main.sql` carefully
   - Look for renamed or removed internal tables that might affect your code

5. **Isolate system from application**
   - Never add triggers or indices to system tables (those live in `app/`)
   - Keep system tables pristine for TrailBase functionality

## Troubleshooting

### Schema is out of sync with application code

```bash
# Plan to see what's drifted
trail declarative plan --db main --schema traildepot/schema/app/main.sql

# Apply to bring database in line
trail declarative apply --db main --schema traildepot/schema/app/main.sql
```

### After updating TrailBase, new system features aren't available

```bash
# Sync the system schema
trail schema export > traildepot/schema/system/main.sql

# Check if application schema needs updates
trail declarative plan --db main --schema traildepot/schema/app/main.sql
```

### Accidentally edited `system/main.sql`

Since system schemas are regenerated, simply discard your changes:

```bash
git checkout traildepot/schema/system/main.sql

# Then re-export to get current state
trail schema export > traildepot/schema/system/main.sql
```
